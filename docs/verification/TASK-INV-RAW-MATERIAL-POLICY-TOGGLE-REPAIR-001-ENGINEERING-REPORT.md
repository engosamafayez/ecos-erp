## 1 — Executive Summary

The proven route-shadowing defect is repaired and the inventory-policy toggle works end to end,
verified by a real HTTP call against `ecos_dev`.

`Route::apiResource('products', …)` registered `update` as `PUT|PATCH`. Laravel returns the **first**
matching route, so the resource shadowed the dedicated `PATCH` declared four lines later: every partial
payload was dispatched to `update()` → `UpdateProductRequest`, whose `sku`, `name`, `category_id` and
`product_type` are all `required`. The toggle sends only `allow_negative_stock`, so it could only ever
return 422, and `ProductController::patch()` was unreachable from the day it shipped.

The verbs are now declared explicitly. `PATCH` resolves to `patch()`; `PUT` still resolves to
`update()` under its original `products.update` name.

**One finding materially shaped the fix.** Un-shadowing `patch()` alone would have exposed an
**unscoped cross-tenant write**: `patch()` used a bare `Product::findOrFail()`, has no `authorize()`
call, no `ProductPolicy` exists, and `PatchProductRequest::authorize()` returns `true`. Certification
criterion **C** requires proven tenant isolation, so the endpoint now applies the **same** RC-6
fail-closed predicate the product list and KPI already use. No new mechanism was invented.

## 4 — Part 2 Route Repair

Neither the public URL nor any verb, name, middleware or permission changed. Only the *declaration*
changed, so first-match can no longer decide the contract:

```php
Route::apiResource('products', ProductController::class)
    ->except(['update'])
    ->middlewareFor('store', 'permission:inventory.products.create')
    ->middlewareFor('destroy', 'permission:inventory.products.delete');
Route::put('products/{product}', [ProductController::class, 'update'])
    ->name('products.update')
    ->middleware('permission:inventory.products.update');
Route::patch('products/{product}', [ProductController::class, 'patch'])
    ->name('products.patch')
    ->middleware('permission:inventory.products.update');
```

**Proof — `php artisan route:list` after `route:clear`:**

## 5 — Part 3 Request Contract

`PatchProductRequest` was **not modified**. Validation was neither broadened nor weakened; no rule was
made nullable to make a test pass.

It already validates only fields belonging to the patch contract — `allow_negative_stock`, `is_active`,

## 6 — Parts 4 & 5 Authorization and Tenant Isolation

### The gap found

Making `patch()` reachable would have exposed an unscoped write: the `permission:` middleware
(`RequirePermissionMiddleware`) checks the **permission only, never tenancy**, and nothing else on the
path checked ownership.

### The fix — the existing certified pattern, not a new one

`patch()` now applies the same predicate as `EloquentProductRepository::paginate()` (lines 57-71) and
`ProductController::stats()` (lines 231-237):

```php
$tenant = app(TenantOwnershipResolver::class);
$query = Product::query();

if ($tenant->appliesTo() && ! $tenant->isUnrestricted()) {
    $companyId = $tenant->companyId();

    if ($companyId === null) {
        $query->whereRaw('1 = 0');
    } else {
        $query->whereHas('brand', fn ($q) => $q->where('company_id', $companyId));
    }
}

$model = $query->findOrFail($product);
```

Ownership runs Product → Brand → Company (ADR-013); privilege flows only through the documented
`is_system` path. No global scope was introduced, and no new permission was created.

| Case | Expected | Result |
|---|---|---|
| Authorized same-company user | ALLOW | **200** ✅ |
| User with a different `inventory.products.*` permission | DENY | **403** ✅ |
| Unauthenticated | DENY | **401** ✅ |
| Company A → Company B product | DENY | **404** ✅ (target byte-identical) |
| Company-scoped actor with `company_id = NULL` | fail closed | **404** ✅ |
| `is_system` actor cross-company | existing semantics | **200** ✅ |

The diagnostic flagged this as unproven because `patch()` had never executed. It is now proven
**isolated**:

## 14 — Operational Consequence the Owner Should Know

The toggle works today for `admin@ecos.local` because that account holds `super-admin` with
`is_system = 1`, so `TenantOwnershipResolver::isUnrestricted()` returns true and the scope does not
apply.

**A non-system company-admin would now receive 404 on `RM-000001` and `RM-000002`**, because both have
**`brand_id = NULL`** and `products` has **no `company_id` column** — so Product → Brand → Company
cannot resolve and the fail-closed branch denies.

This is **not new behaviour introduced here**: `EloquentProductRepository::paginate()` already hides
brand-less products from non-system users, so those users cannot see these two materials in the list
either. The endpoint is now *consistent* with the list and the KPI rather than more permissive than
both.

The underlying data gap — raw materials with no brand, and therefore no resolvable tenant — is real and
belongs to a separate task. Recommended: populate `brand_id` on raw materials, or decide whether
`products` should carry `company_id` directly. **No product data was modified by this task.**
