## B — Create Group HTTP 500 (root-caused and fixed)

**Root cause:** the manual "+ Create Distribution Group" panel computed its `code` client-side as `DG-${visibleGroups.length + 1}`, scoped to the groups currently visible (open, this warehouse). The database's real uniqueness constraint (`dist_slots_window_code_unique`) is scoped to the **whole window** — every warehouse, every Wave, closed or not, and closed Groups are never deleted (only stamped `closed_at`). The first manual create after an earlier Wave or a second warehouse had already used that guessed code collided, threw an uncaught `Illuminate\Database\QueryException` (MySQL 1062), and reached the client as a raw 500 (`storeSlot()` had no catch; `bootstrap/app.php` renders no response for `QueryException`). Proven as a real, recent regression via `git log` (two commits from six days before this task correctly started closing manual Groups with their Wave, but never updated the code generator to match).

**Fix:** `code` is now optional. Omitted, `DistributionWindowController::createSlotWithSafeCode()`/`nextGroupCode()` compute the next `DG-###` from **every** row in the window (matching the constraint's real scope exactly), with a bounded regenerate-and-retry loop for the genuine concurrent-insert race (mirroring the pattern `DailyGroupLifecycleService::ensureGroupForTemplate()` already uses for the same class of problem). A caller-supplied `code` is still honoured verbatim but a real collision is now a clean 422 (`DistributionException::groupCodeAlreadyInUse()`), never a 500 — the catch is narrowly scoped to the specific named unique-index violation, so an unrelated DB fault still surfaces as a 500 rather than being silently mis-reported as "code taken". Frontend (`distribution-groups-panel.tsx` and friends) no longer guesses a code at all. Three new tests prove the two collision scenarios plus the clean-rejection case.

## C — Preferred Driver + Vehicle

Group Templates may now carry an optional `preferred_driver_id`/`preferred_vehicle_id` (new nullable, indexed bigint columns, migration `2026_09_09_100000_...`). When a Group is generated (the §A sweep), `GroupTemplateService::attemptPreferredAssignment()` tries to assign them by reusing `GroupVehicleAssignmentService::assign()` verbatim — the one place every availability rule already lives (tenant scope, `canBeDispatched()`, capacity, pairing-ledger exclusivity, Trip-engagement). **Preference never overrides availability**: any `FleetAssignmentException` is caught, logged at info level, and silently leaves the Group unassigned exactly as if no preference existed. A one-sided preference (only a driver, or only a vehicle named) is completed using that entity's own *current* active ledger pairing, never an invented one; with no such pairing, the attempt is skipped.

**A real, pre-existing gap closed as part of this:** Distribution's availability checks excluded a vehicle busy in active Operations\Loading work (`loadingBusyVehicleUuids()`) but had **no equivalent check for the driver side** — a driver already committed to an active `driver_assignments` row could still be paired to a new Group. Added `GroupVehicleAssignmentService::loadingBusyDriverUuids()` (mirroring the vehicle-side predicate, reading `DriverAssignmentStatus`'s own terminal set directly) and wired it into the shared `assign()` guard chain. **Note for whoever picks this up next:** this is a behavior change for the pre-existing *manual* "assign vehicle" endpoint too, not just the new preferred-assignment path — a manual assignment that was previously (incorrectly) allowed for a Loading-busy driver will now be correctly refused with a 422. This is a bug fix, not a regression, but is called out explicitly since it changes what the endpoint accepts.

## E / F — Loading Session / Wave lifecycle custody, and Waiting-on-Driver

**This was the real gap in the whole ticket.** Confirmed by direct code reading: Wave closure (`DailyGroupLifecycleService::closeWave()`) only ever released Orders from their Group and stamped the Group's own `closed_at` — its own listener's docblock says outright "it does not... touch a Trip, Driver, Vehicle or Loading record." Nothing anywhere closed an in-flight Trip or its Loading execution when the Wave that produced it ended, so a loading in progress — or a Trip sitting "waiting on driver" at the Dispatch Gate — could survive a closed Wave/day indefinitely, with no terminal outcome, ever.

**New `WaveClosureCustodyService`**, reacting to the same `WaveClosed` event via a **second** listener (`CloseWaveLoadingCustodyListener`, registered directly in the service provider since the existing convenience map holds one listener per event and `WaveClosed` already had one) sweeps every non-terminal Trip under a closing Wave's Groups:

- **Driver accepted custody** (`Trip::hasFullDriverAcceptance()` — this codebase's own established "custody boundary", per its use in `Trip::isTrackable()`'s docblock from an earlier task) → left completely untouched.
- **Not accepted** (whether real goods were loaded first or nothing ever loaded) → the Loading execution (`VehicleAssignment` → `Cancelled`) and the Trip itself are cancelled, and every still-active Order on that Trip is released back to the pool via the **existing** `TripService::releaseOrder()` primitive — nothing is deleted, so the loaded/attempted history stays intact for §G's audit trail. The recorded reason distinguishes `wave_closed_loaded_not_accepted` from `wave_closed_not_loaded` for exactly that audit purpose. An Order's `status` is never touched by this — it was never anything but its own pre-existing status, since nothing in this codebase marks an Order dispatched before its Trip reaches `Dispatched`, which itself requires acceptance.

This is best-effort per-Trip (one Trip's unexpected failure is logged and skipped, never allowed to block Wave closure itself, which is the older, already-relied-upon operation) and idempotent (a replayed `WaveClosed` finds nothing left to do, proven by test).

**Deliberate scope boundary, flagged rather than silently decided:** `LoadingSession.status` (the warehouse+day parent record, shared across every Wave/Group active that day) is **never** touched by this sweep. A session can legitimately still have other, genuinely active work from a different, still-open Wave underneath it — advancing or cancelling the parent based on only the closing Wave's children would risk falsely completing or killing that unrelated work. The **observable** requirement is still met: §G's classifier already routes a Trip's cancelled `VehicleAssignment` into the Completed/History bucket per-child, regardless of what the parent session's own status column says. What is **not** claimed: the raw `loading_sessions.status` DB column itself will not necessarily read `cancelled`/`closed` in this scenario — only its children's true state, and what the History view shows, are guaranteed correct.

**Also discovered, explicitly out of scope for this task:** `Modules\Operations\Fulfillment\Application\Workflows\DispatchOrderWorkflow` (the "direct dispatch, no loading OS" path — `POST /api/fulfillment/orders/{order}/dispatch`, the generic `PATCH /orders/{order}` status transition, and bulk dispatch) guards only on `Order.status === ReadyForDispatch`, with **zero** awareness of Trip/Loading state or either custody mechanism. An Order sitting mid-load (or even fully loaded but unconfirmed) on an active Trip could, before and after this task, still be directly dispatched through that separate endpoint, bypassing custody entirely. This predates this task, sits in a different module (Commerce/Fulfillment, not Distribution/Loading), and fixing it risks breaking the legitimate orders that are deliberately never routed through Loading OS at all — it was not touched here and is flagged for a future task with the right scope to address it safely.

## G — Completed / History

Fixed the actual defect: `LoadingWorkspaceClassificationService::classifySession()` was explicitly routing a session with zero `VehicleAssignment` children into the `completed_history` bucket (tagged `no_activity`) — meaning a genuinely never-started **Draft** session (the common case for zero activity) was shown as "completed". It now returns `null` (excluded from every bucket and every count) unless the session's own status is actually terminal (`Closed`/`Cancelled`) — the one legitimate case where zero activity really is history (e.g. an operator cancelled it before anything was ever assigned).

History rows now also carry the audit detail the task asked for, resolved in the controller (Trip → Group → Wave, and Trip → its Orders, cross-module lookups that belong at the Distribution-Presentation layer already crossing this boundary for `transport`, not inside the Loading-domain classifier): **Wave** (number, planning date), **Group** (code, name), **Orders** (order number, and whether each was released back to the pool), **loaded quantity**, **driver-accepted quantity**, the **unaccepted/returned difference**, **closure time**, and the **terminal/cancellation reason** — alongside the Trip/Driver/Vehicle/final-status detail the endpoint already returned. Frontend renders all of this specifically in the Completed/History tab (the other three tabs are visually unchanged).
